# The crawl boundary

The crawl engine was chosen by a benchmark. Two candidates ran the same seeds under the same nominal limits, one covered roughly twice the pages and surfaced non-200 responses, and it won on that evidence. Evidence expires: a benchmark is a measurement of one afternoon, engines change, and the next site that has to be archived may be the one this engine handles worst.

So the engine is a dependency behind a line, not a foundation the archive is built on. This document is what the line is made of, and what a second engine would have to provide to replace the first.

## What crosses the line

Three types, all of them written in the archive's terms rather than an engine's.

- **`Seed`**, going down: where a crawl starts and the limits it stays inside, which are a page count, a depth, a concurrency, a delay, the execution policy below, and whether the seed may name an address that exists only inside a network. The page count, depth, concurrency and delay are the settings the benchmark ran under, so a run started with them produces a known result.
- **`PageEvent`**, coming up: either a response or the report that there was none. A response carries the requested URL, the final URL, the status, the response headers with every repeat a name sent, the body, whether that body is all of it, and when the fetch happened.
- **`CrawlOutcome`**, at the end: what the crawl lost, and why it ended. Today the loss is the count of pages the engine fetched and the archive never received, and the ending is one of three: nothing left to fetch, the budget gone, the caller having asked to stop.

Everything else an engine knows about, its configuration surface, its concurrency model, its idea of what a page is, stops at the adapter.

Two things are asked of an engine rather than one: a crawl, and a single URL fetched on its own. The second exists because a page's subresources cannot be acquired through the first. Handing those addresses back to the crawl would file each of them as an item with a depth and a queue position, when a subresource belongs to the capture that referenced it and to nothing else. The fetch carries the same `Seed`, for the policy on it rather than for the address in it: the request timeout, the redirect screening and the rule about internal addresses govern every request a run makes, not only the ones the engine chose to make. It answers with a `PageEvent` and never an error, because everything that can go wrong is a fetch that produced no response, including a URL the engine refused to dial at all.

## The decisions in it

**The call blocks and the core stays synchronous.** The engine is asynchronous underneath, and its runtime is built inside the adapter and never escapes. An archive is a directory being written; making canonicalization, storage and every test above them async so that one dependency feels at home is the dependency dictating the shape of the program.

**A single fetch happens on a thread of its own, and that is not an optimization.** It is called from the page callback of a crawl, which runs on a thread that is already driving the engine's runtime, and a runtime cannot be entered from there. Doing the work on that thread would panic on the first subresource of the first page. The same thread also contains a panic inside the engine to the one subresource it happened on, rather than to the site the run was still archiving.

**Pages arrive one at a time, through a callback, while the crawl runs.** A crawl that returns a list has already held a run's worth of response bodies in memory, and has produced nothing if it is interrupted at page 199.

**The callback answers with a `ControlFlow`.** The caller is the one who knows when continuing is pointless. One case is a failed write: the disk that refused this capture will refuse the next one, and a crawl that keeps fetching after that spends a site's bandwidth on nothing. Breaking cancels the crawl rather than draining it. The other case is the seed's deadline, which is described below.

**A non-200 is a response like any other.** An archive that keeps only successes cannot answer why something is missing from it, and a 404 recorded on a date is the evidence that the page was already gone then. The benchmark's losing candidate reported only successes, and that counted against it.

**A fetch that reached no server is not a response, and the boundary says so.** This is not a detail of one engine, it is the reason `PageEvent` has two shapes. A DNS failure, a refused connection and a TLS error produce no status, no headers and no body, and an engine with nowhere to report that invents them: this one answers 599 for a failure to send and 524 for a connection timeout. Archiving that would put a status in the record that no server ever sent, and a later reader has no way to tell it from a proxy that really answered 599. The URL and the reason are reported instead, and nothing is stored.

**The identity of a capture comes from the final URL, not the requested one.** After a redirect the content is at the destination, and filing it under the address that pointed there gives one page a second identity for every link that reaches it. Both URLs are kept in the record, so nothing about the fetch is lost. [`docs/canonicalization.md`](canonicalization.md) has the rules that turn that URL into an address.

**A page the canonical rules refuse is skipped and reported, not fatal.** One URL the archive has no address for says nothing about the other two hundred. The run carries the URL and the reason, so the refusal can be looked at rather than counted.

**A lost page is counted, never inferred.** The queue between the engine and the archive is bounded: sized to the fetch concurrency alone it would drop pages as soon as a write is slower than a fetch, and sized to the page limit it would hold a whole crawl's bodies in memory. It is sized between the two, and what overflows anyway is counted into the outcome. A caller that breaks out early counts what it leaves queued the same way, since those pages cost a fetch each and the archive does not have them; that count is a floor, because a fetch still in flight can queue another page after the queue was measured. Silently archiving less than was fetched is the failure this project can least afford.

**A link the crawl discovered and never fetched is counted too, even though nothing was spent on it.** At a concurrency of one, a page that discovers more than one followable link loses one of them to the engine's own frontier about half the time: the engine decides it has nothing left to do by asking whether its own accumulator of newly found links is empty and no task is in flight, without asking whether the batch of links it already knew about when that check ran still had one left to dequeue. A concurrency of one is exactly what starves that check into running early, since only one fetch is ever in flight to keep the accumulator from looking empty. The crawl still ends by reporting `Exhausted`, no fetch failed, and no warning fires, so the loss is invisible unless something outside the engine goes looking for it. `hop_depth_guard` already tracks, for its own reason, every same-host link a fetched page discovered inside `max_depth`; comparing that record against the URLs `crawl_seed` actually handed to the caller, once the crawl claims to be done, is what surfaces the difference. A link left over because `max_pages` was reached is excluded on purpose, since that is the budget working as asked rather than the engine dropping something. The dependency is not patched for this: rewriting its frontier would mean owning a crawl loop this project does not want to own, so what exists instead is the report, which is exactly the shape `docs/cli.md`'s exit code already reserves for a run holding less than it found.

**A page counted into `pages_dropped` is excluded from the comparison entirely, not folded into it as another allowed loss.** `frontier_claim_is_trustworthy` gates the report on two conditions rather than one: `CrawlStop::Exhausted` says nothing was left in the engine's own queue, and a `pages_dropped` of zero says nothing was lost between the engine and the caller either. A page the queue between them dropped never reaches `on_page`, so it is missing from `fetched` without any budget having refused it, and comparing `depths` against `fetched` while even one page is missing that way reports every link the crawl genuinely left in the frontier behind the lost page as though this guard had caught it, which on a run that lost only a couple of pages out of a large crawl turns one honest count already sitting in the report into thousands of lines restating it.

**A link `robots.txt` disallows is excluded by asking the engine, not by a second opinion about what it disallows.** A page that links a path the site's own rules refuse is not the frontier dropping anything, and reporting it as a loss would make every capture of a real site fail on exactly the runs that matter, since a publication that disallows a path linked from every one of its pages would exit non-zero on every single capture. The comparison above asks `Website::is_allowed_robots`, the same predicate the engine's own frontier already consulted before declining to queue the link, rather than reading `robots.txt` a second time in this file: two implementations of the same rule are not guaranteed to agree, and this project already knows one way they would not, since the engine's parser cannot match a `Disallow` line with an interior wildcard and so under-refuses rather than over-refuses there. Reimplementing the rule here would then report the gap between the two parsers as data loss, on the sites where the exit code matters most. Asking is sound at the time the comparison runs: the parser is built and `robots.txt` is read during the engine's own setup, before the first page is ever fetched, so by the time a crawl has finished it is already the same parser that decided everything the crawl itself declined. A site that served no `robots.txt` at all, or a run with the check turned off, answers the question the same way the engine's own frontier does, which is to allow everything.

**A link resolved from the same href two ways was the remaining risk, and three of the four shapes it took are closed by forcing the same spelling `push_link` already forces before a link reaches the frontier.** `hop_depth_guard` resolves an href against the page it was found on to build its own record of what was discovered; the engine resolves the same href to decide what its frontier actually requests. `depth_key` now forces both records onto `frontier_scheme`, the seed's own scheme read once at the start of the crawl, before comparing them, exactly as `push_link` forces the scheme of every resolved, in-scope link to that same value before it is ever queued: a page carrying a hardcoded self link in the other scheme, or the mirror of that on a site typed the other way around, is archived under the seed's scheme regardless of which scheme the href itself named, and is never reported lost for it. The same loop refuses a same-host link whose resolved scheme is neither `http` nor `https` before it is ever recorded, since `validate_link` drops one there too: an `ftp://` link is never dialled by the engine and this adapter no longer expects one to be. What is still open is `<base href>`: the engine resolves every later link on a page that declares one as an absolute URL against that value instead of against the page's own address, and `hop_depth_guard` has no way to resolve against the same base without a second HTML parse of its own. The answer chosen is to record nothing about such a page's links at all, in `page_declares_an_absolute_base_href`, rather than resolve against the wrong base and report an address the site never had as lost; the cost is a depth reading on that page's own links, which fall back to being read as one hop from the seed the same way a page this cannot place already does, and that is far cheaper than failing a whole run over a page using a real HTML feature. Measured against real shapes pages are written with, an href entity-encoded (`&amp;` for a literal `&`) and one already percent-encoded, both are still followed and archived without being reported lost, because the engine's own link extraction turns out not to decode the entity in either this project's resolution or its own before either one builds a URL from it: the two sides still agree, so nothing here disagrees with anything else, even though the archived address is a mis-parsed one. That is a real defect, and a different one: it corrupts what a link is filed under rather than losing the link, and it belongs to whatever reads `page.page_links` for its href text before either resolution runs. What remains unproven, because it has not been measured, is whether every other way an href can be written, a differently-cased host, a relative path with `..` segments, an internationalized domain, resolves identically on both sides; nothing currently known says it does not.

**The execution policy is three numbers on the `Seed`: a deadline, a request timeout, and a retry budget.** The benchmark's clearest finding was that a per-page limit is not an execution policy, since one of its domains spent 402 seconds of a 573 second run. What bounds that is wall-clock time, and the number is an archival decision: it says how much of an afternoon one site is worth, which no engine can know.

**A seed is one host, so the per-seed budget is the per-domain budget.** Subdomains and other TLDs of the same name are separate seeds by construction, and a crawl started at one address never leaves it. There is no second, narrower per-domain knob because there is no second domain for it to apply to. What was genuinely missing underneath the deadline is a ceiling on a single request, which is a different thing entirely: at the default concurrency, one connection a server accepts and then holds open owns a sixteenth of the run until something closes it. The engine's own default for that was 120 seconds, which is a third of the default deadline spent by one dead socket.

**The request timeout reaches the HTTP client, and a request that outlives it is reported as the failure it was.** The engine cancels it and surfaces a transport error, which crosses this line as a `NoResponse` like a DNS failure does. That is worth saying because the engine has a second mechanism for the same symptom, its first-byte watchdog, which answers a stalled request with a 504 it invented, carrying no body and no error mark. That one is off, and a test asserts it stays off: the boundary would read its output as a response a server sent.

**Retry belongs to the engine, its budget belongs here.** Retrying is fetching again, and the engine is the only thing that fetches, so what it repeats and how long it waits are its rules: a 429, a 408 or a server error the second attempt could answer differently, never a DNS failure, a redirect loop or a refusal to speak the protocol at all, and between attempts the longer of an exponential backoff and what the response asked for, which for a 429 is its `Retry-After`. How much of the seed's budget to spend on repeating rather than on new pages is the archive's call, and that is the number on the `Seed`. It multiplies the request timeout rather than sitting beside it: a URL that keeps timing out is paid for once per attempt, so two retries at a thirty second ceiling put a single dead URL at ninety seconds and the waits between them, which is what makes both numbers one decision instead of two.

**The deadline is the engine's to enforce, and the guard above it arrives late on purpose.** A host that accepts the connection and then says nothing produces no page at all, so nothing above the boundary ever gets a turn to notice, which is why the adapter is where the budget is really spent: it cancels the crawl when the timer it owns expires. The pipeline above keeps a second check for the failure the first one cannot cover, an engine that ignores the field entirely, and that check fires a margin after the budget rather than on the instant. The margin is the difference between a backstop and a race. An engine that honors the deadline is, at that exact moment, handing up the pages it had already fetched, and a guard that broke out on the first of them would count the rest as lost, which is the opposite of what the paragraph below promises. A tenth of the budget is far more than a queue of local writes needs and still bounds an engine that does nothing. The page in hand when a guard does fire is archived and the run ends after it, because that page was already fetched and refusing to write it spends the bytes without keeping anything.

**The deadline bounds fetching, not the writing of what was already fetched.** When it fires, the pages sitting in the queue are handed over and then the run ends. They are in memory, they cost their bytes before the budget ran out, and the work left is local. What they are not is waited for: a cancelled crawl leaves senders in tasks that are still winding down, so the queue is read for what is in it rather than read until it closes, which would hand the end of the run back to the thing the deadline just took it from.

**The engine's own crawl timeout was rejected for the deadline.** It stops the engine from queueing new links once the budget is gone, but it also applies that same budget again as a ceiling on each individual fetch, so a run can finish at roughly twice its deadline. A deadline that is approximately a deadline is not one. The adapter races the crawl against a timer it owns instead, which ends the run at the number that was asked for.

**The engine is configured against the archive, not against its own defaults.** Two of its features had to be turned off rather than inherited: one spools a large response body to a temporary file and then reports an empty body, which would store a page as though it had arrived, and one attaches a browser fingerprint to every request, which is the opposite of a crawler that says who it is. Both are silent, and both would have been shipped by taking a bundle. `Cargo.toml` carries the list and the reason.

**The seed is checked before the engine dials anything, for its scheme and for its address.** `file:` or `data:` reaching a crawler is the archive reading the local machine. The address matters for the same reason and is the half the engine cannot cover: it screens every redirect hop for loopback, private, link-local, unspecified and broadcast addresses and for the names a cloud metadata service answers on, and it dials the seed straight past all of that. A seed naming 169.254.169.254 reached the credential store of whatever machine the archive runs on, and a seed naming 127.0.0.1 reached its ports. The same ranges are refused on the way in, along with the fully qualified spelling of internal names, because `localhost.` and `metadata.google.internal.` are the same names as their unqualified forms. Archiving a site served locally stays possible and has to be asked for, which is not a convenience: pointing the crawler at a server on localhost is the only way the fetch path is exercised at all, so a guard with no way through would have closed the project's own check along with the hole.

**The same check is also askable on its own, before a crawl starts.** A crawl screens its own seed, so `check_seed` answers a question that would be answered anyway, and it exists for the caller with something to commit first. Opening an archive is what brings one into existence, so a command line that opened the archive and then discovered the seed was unusable would leave an empty collection sitting on the path that was typed wrong, which is precisely the case the line announcing a new archive exists to make visible. Asking first costs nothing: nothing is dialled either way.

**Neither half of that guard resolves the name.** A domain answering with a private address passes both, and closing that means resolving before the connect and pinning the answer at connect time, since a name is free to answer differently the second time it is asked. That is a resolving connector rather than a string check, and it is the part of this that is not built.

**A page that ended inside a network is refused before it is stored, and the same predicate decides it.** The seed is screened before anything is dialled, so a page wearing one of these addresses got there through a redirect, which is screened inside the engine's HTTP client by a policy with no entry point here. The archive keeps its own check anyway: the engine is replaceable, the stored response outlives the run, and fully qualified internal names are normalized here before they are matched. Refusing at the store step does not un-send the request, and it is not meant to. For an archive the durable copy is the harm, since a fetch nobody reads costs a connection while a stored response is the local network answering into a directory that outlives the run, so the guard is placed where it can still refuse rather than left out because it is late. The page is reported and the crawl continues, like a URL the canonical rules refuse: one address says nothing about the other two hundred. It reads the same flag as the seed, so a run that asked for local addresses still archives them, and the manual check against a server on localhost keeps working.

**A redirect off the seed's host is recorded rather than followed, after the first two of a run.** Identity comes from the final URL, so a hop that leaves the seed's host files the page under an address nobody asked for, which quietly undoes the rule that a seed is one host. Under the stricter of the engine's two screening policies that hop is not followed and the redirect itself is archived, which is the honest record of what the host said. The exception is an allowance of two hops, which exists so that an apex can redirect to its www form and an http seed can reach its https one, and it is a counter shared by the whole run rather than one per request. A crawl that meets three off-host redirects therefore follows two of them and records the third, and which two is decided by whichever requests arrive first. Measured against a local site: of four pages redirecting off the host, the first two were followed and the last two were archived as the 302 they answered with. The chain limit is spelled out at the same value the engine defaults to, because a loop that ends by exhausting the crawl's budget spends a whole seed on one URL.

**One response may spend sixty-four megabytes, and what exceeds that is kept and marked.** This is the only limit here whose absence costs more than the record it applies to: a response that declares no length is read until it ends, and one that never ends fills memory until the process dies with the whole run inside it. The engine's own ceiling is two gigabytes and applies only to a response that declares its length, which is to say only to the responses that were never the problem. The number reaches the engine through the environment, because both of its configurable byte limits are browser-only and do nothing in this build, so it is process-wide rather than a number on the seed and is applied before the first crawl builds its runtime. A value already in the environment stands, including a zero meaning no ceiling.

**A body that arrived short says so, and that is a field on the record rather than an inference.** A transfer ends early for reasons that have nothing to do with the server changing its mind: a stream that errors, one that goes idle mid-transfer, one that runs past the ceiling above. The bytes that made it still parse and still arrive under a status that promises the whole page, so without the mark the archive is quietly wrong instead of visibly short. It covers the shape the engine leaves unlabelled as well: a response whose declared length is over the ceiling is handed over with real headers and no body at all, and stored as an empty page that is the exact corruption a ceiling exists to prevent. A status that sends no body of its own is exempt, since the etag cache produces 304s and a 304 repeats the length of the entity it is deliberately not sending. The mark is part of the capture fingerprint, because two fetches can agree on every byte they kept and disagree on whether that was all of them.

## What is deliberately not here

- **A seed whose name resolves to a private address.** The guard reads addresses and known names, not answers from a resolver, so a domain pointed at 10.0.0.1 is fetched.
- **A hard rule that no page is ever archived under a host the run was not pointed at.** The allowance above is the engine's, not a decision made here, and closing it means refusing the capture above the boundary rather than the fetch below it, where the seed's own move to its canonical host would have to stay allowed.
- **A subresource inside a page event.** A page event carries the page. The subresources it needs are their own pass, over the single fetch above, and [`asset-capture.md`](asset-capture.md) is where its rules live.

## Testing it

The pipeline above the line is tested against a scripted engine that replays written-down page events, so what the archive does with a 404, with a redirect or with a URL it cannot address is decided by the test rather than by whatever the web answered today.

In the adapter, everything that does not need a socket is tested the same way: the queue that can lose pages is driven directly with a channel and more pages than it holds, and the translation from the engine's page to a page event is checked on a page built by hand. The deadline is the same trick applied to time. The crawl reaches the place that enforces it as a future rather than as a website, so the stalled host that the whole policy exists for is a future that never finishes, and the run that has to end at its budget can be proven to in fifty milliseconds. The margin the guard above the boundary waits out is a plain function of the budget and the elapsed time, which is why the one behavior that would otherwise need a stopwatch and a sleeping test is three assertions instead. The numbers that only the engine can act on, the request timeout, the retry budget and the redirect policy, are checked where they land in its configuration, since a change to how the engine is configured otherwise compiles and passes every gate while being broken.

Two of the tests that open a socket cover something that lives inside the dependency with no reachable entry point. The rule they read against is about the web rather than about sockets: nothing in them leaves the machine, needs setup, or answers differently tomorrow, because the server they crawl is in the same file.

The first is the redirect guard. Whether a hop into a private address is followed is decided inside the engine's HTTP client, by a policy with no public entry point and no constructible input, so asserting which policy was configured proves the configuration and not the refusal. That test starts a server on a loopback port, answers the seed with a redirect into 169.254.169.254, and checks that the hop produced no record.

The second is the single fetch, and what it really covers is the thread the decision above is about. Nothing can assert that a runtime is not being nested without running one, and getting it wrong is a panic on the first subresource of the first page. So a server serves a page, a stylesheet and an image whose bytes are not text, and the test asserts that the archive holds all three and that the only paths asked of that server were the four it should have been.

A third crawls the same page repeatedly rather than once, because the frontier defect the paragraph above describes is a race and shows up only some of the time. At a concurrency of one against a page with two sibling links, that test runs the binary thirty times and checks two things on every run: a run that leaves with a clean code holds all three pages, and a run that leaves with a failing one names the link it never fetched. Thirty runs make a coin flip that happened to hide from every one of them a chance of about one in a billion, so the test also fails outright if none of the thirty runs ever loses a link, since a version of it that stopped exercising the race it was written to catch would otherwise pass by saying nothing. That site's own `robots.txt` answers 404, which is what makes every loss it reports the genuine one rather than a rule the crawl was right to respect.

A fourth crawls a page that links a path a real `robots.txt` disallows, at a concurrency the race above does not reach, and checks that the run leaves with a clean code holding the page the rule allows and none of the one it refuses: the guard has to agree with the rule rather than report the refusal as a loss. A fifth crawls a page whose two links are spelled the way pages in the wild spell them, an entity inside a query string and a percent-encoded character, and checks that both are archived and neither is reported lost, which is the empirical answer to whether this project's own resolution of an href and the engine's agree on what they resolved.

A sixth crawls a page carrying an absolute self link in the other scheme from the one the seed was typed with, and checks that the linked page is archived and never reported lost, since the engine forces the seed's scheme onto a link before queueing it and this record has to be spelled the same way. A seventh crawls a page that declares an absolute `<base href>` and links relatively against it, and checks the same thing for the page reached through the rewritten base, pinning the trade `page_declares_an_absolute_base_href` makes. An eighth crawls a page carrying a same host link in a scheme the engine will not dial, `ftp://` being the one seen in the wild, and checks that the ordinary link beside it is archived while the FTP one is neither fetched nor reported lost. The last of the four, that a page the queue dropped defeats the `max_pages` suppression above and turns every link the budget legitimately left behind into a false report, is pinned by a unit test directly on `frontier_claim_is_trustworthy` rather than by a ninth loopback crawl: forcing a real queue overflow deterministically over loopback needs either an artificial delay or a page large enough to make a real archive write outrun a real fetch, and neither buys more confidence than exercising the exact boolean the production code branches on, for both of the values it can take.
